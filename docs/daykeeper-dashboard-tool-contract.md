# Daykeeper Dashboard MCP tool contract

This hosted server uses the candidate `@skyporch/daykeeper` SDK. The API returns `{ data: ... }`; the SDK unwraps that envelope, and the MCP adapter maps the SDK values to the stable app result shapes below. Tool arguments do not include organization or tenant IDs. The adapter picks the oldest-created tenant whose state is `ready` and whose `spec.inbox.type` is `api`, breaking timestamp ties by tenant ID. If none exists, tenant operations fail with an unavailable result; there is no fallback to an unready, website, or provisioning tenant.

The selected API tenant is derived from the OAuth-bound `tenants.list()` result on each tool call. The OAuth grant itself is bound to one organization/workspace, and the management API enforces that organization and tenant access. The user cannot use tool input to widen either boundary.

| Tool | Input | SDK call | Normalized result | Scope |
| --- | --- | --- | --- | --- |
| `get_profile` | `{}` | `profile.get()` | `{userId,name,email,workspaceId,workspaceName,workspace:{id,name}}` | `daykeeper.accounts:read` |
| `list_workspaces` | `{}` | `workspaces.list()` | `{workspaces:[{id,name}]}`; only the OAuth-bound workspace is returned | `daykeeper.accounts:read` |
| `get_dashboard` | `{}` | `tenants.list()`, `entitlements.get()`, `usage.get()`, and `inboxes.get(selectedTenantId)` when selected tenant state is ready | `{readiness,plan:{name},usage:{used,limit,periodLabel,startsAt?,endsAt?}}`; absent counts remain null | `daykeeper.accounts:read` + `daykeeper.billing:read` |
| `list_conversations` | `{cursor?,limit?}` | `operatorConversations.list(tenantId,{cursor,limit})` | `{conversations:[{id,label:"Conversation #ID",preview,updatedAtLabel,status}],page}` | `daykeeper.conversations:read` |
| `get_conversation` | `{conversationId,cursor?,limit?}` | `operatorConversations.get(...)` and `.messages(...)` | `{conversation:{id,label:"Conversation #ID",status,messages:[{id,role,authorName,body,createdAtLabel}],page}}` | `daykeeper.conversations:read` |
| `send_reply` | `{conversationId,body,requestId}` | `operatorConversations.reply(...,{requestId})` | `{sent:true}` | `daykeeper.conversations:write` |
| `set_conversation_status` | `{conversationId,status:"open"|"resolved"}` | `operatorConversations.setStatus(...)` | `{conversation:{id,status}}` | `daykeeper.conversations:write` |
| `get_customer_email` | `{}` | `customerEmail.get(tenantId)` | `{enabled:boolean}` | `daykeeper.accounts:read` |
| `set_customer_email` | `{enabled:boolean}` | `customerEmail.set(tenantId,{enabled})` | `{enabled:boolean}` | `daykeeper.accounts:write` |
| `show_dashboard` | `{}` | Local resource handoff | `{opened:true}` and `_meta.ui.resourceUri="ui://daykeeper-dashboard/dashboard.html"` | `daykeeper.accounts:read` |

`send_reply.requestId` is required by the MCP schema and must be a UUID generated by the caller for the exact logical reply. Keep it unchanged across uncertain outcomes and do not retry automatically. The handler has no retry loop. The management API stores a payload hash and provider message ID, not a transcript copy.

Conversation query defaults are `limit=50`; conversation limits are 1–100 and message limits are 1–200. Message pages are chronological within each page and a cursor retrieves older messages. `page.hasMore` may be `true` conservatively and an extra empty page is acceptable. If pagination metadata is absent on an older API, the MCP output keeps `limit`/`hasMore` null instead of interpreting missing metadata as complete history. The UI may display a summary preview, but it must not claim a page is the full conversation history unless `hasMore` is false.

The gateway adapts provider pagination: conversations use `status=all`, `sort_by=last_activity_at_desc`, and a fixed provider page of 25; the cursor preserves page and offset when the requested limit is smaller. Messages use fixed batches of 20 and the provider's `before=<oldest returned id>` query. Reply reconciliation scans bounded older batches for the UUID provider marker; absence within that bound remains unknown and never triggers a second provider POST.
